## Fractional multiplier display — confirmed source/arithmetic defect

The compact HUD, queued placement text, ledger heading and `ScorePerformance.number` each use `fractionLength(0...2)`. They present the resulting value as the multiplier, without an approximation indication. A legal ordinary acquisition example requires only one Syndication: own it through one won puzzle, then use its ×1.25 alongside Stop the Presses ×3 against Budget Cut ×0.5. Actual Mult is **1.875**. A five completing its row and box queues **50 + 45 + 45 = 140** Points and banks **floor(140 × 1.875) = 262**. Foundation prints that multiplier as **1.88**, for which the displayed arithmetic instead implies **floor(140 × 1.88) = 263**. This is reachable catalogue arithmetic at normal score sizes, not a ceiling fixture.

Independent Foundation execution confirmed the original strings: 0.625 → `0.62`, 1.875 → `1.88`, and 2.8125 → `2.81`. One grown Rolling Presses ×1.5 added to the legal example produces 2.8125, so three decimal places would still be insufficient. Ordinary Shop excludes already-owned Bookmark definitions; no duplicate Syndication is needed or assumed. Engine arithmetic is correct.

Root's build-16 repair now shares `ScorePerformance.number` with up to eleven fractional digits across the live HUD, queued placement receipt, ledger heading, animation operations and running totals. Independently re-read all affected calls: adaptive HUD sizing measures the complete newly formatted queue string. The added `testFractionalCatalogueMultStaysExactThroughPreviewBankAndReceipt` makes an actual row/box-clear placement, asserts 140 Points, Mult 1.875 and bank 262, then checks the explanation, bank animation values and saved ledger. The existing compact HUD rendering loop also covers 1.875 and supported historical duplicate precision 1.52587890625. A remaining two-decimal string in the fixed tutorial only receives the lesson's integer Mult values and is not evidence of another reachable fractional defect. Status: **source recheck passed; new app runtime regression and native receipt rechecks pending**. This reviewer has not run an app build/test or Simulator action for this recheck.
